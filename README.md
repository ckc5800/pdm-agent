# pdm-agent

![CI](https://github.com/ckc5800/pdm-agent/actions/workflows/ci.yml/badge.svg)

설비 센서 시계열에서 이상을 탐지하고, LLM이 정비 진단 리포트를 쓰는
예지보전(Predictive Maintenance) 데모.

음성 AI에서 실시간 신호를 다뤄온 경험을 산업 설비 도메인으로 옮겨보고 싶어서 만들었다.
진동 RMS든 음성 파형이든, 시계열에서 이상 패턴을 찾는 문제의 골격은 같다.

## 설계 원칙: LLM에게 탐지를 시키지 않는다

```
시뮬레이터 ──▶ 이상 탐지 (결정적 알고리즘) ──▶ LLM 진단 (해석·권고만)
 결함 주입      z-score / EWMA / 추세+RUL        탐지 근거 밖 수치 생성 금지
```

이상 탐지는 재현 가능해야 하고 새벽 3시에도 같은 입력에 같은 답을 내야 한다.
그래서 탐지는 통계/신호처리 알고리즘이 하고, LLM은 탐지 근거를 종합해
사람이 읽을 진단서를 쓰는 역할만 맡는다. 프롬프트에서 "근거에 있는 수치만
사용하라"고 제한해 hallucination을 차단했다.

## 탐지기 구성

| 탐지기 | 잡는 것 | 방법 |
|---|---|---|
| z-score | 순간 충격 (낙하물, 이물질) | rolling window 기준 z > 5 스파이크 |
| EWMA | 지속적 수준 이탈 (과열 등) | 초기 구간 기준선 + 4σ 관리한계 초과 |
| 추세 | 점진적 열화 (베어링 마모) | 선형회귀 기울기 + 한계치 도달 시간(간이 RUL) 추정 |

시뮬레이터는 회전기계를 단순화한 모델로, 8시간 주기 부하 변동 위에
결함 3종(순간 충격, 점진적 베어링 마모, 일시 과열)을 주입한다.
주입 시점이 ground truth로 남아서 탐지기를 정량 평가할 수 있다.

## 실행

```bash
pip install -r requirements.txt   # httpx 하나 (탐지기는 표준 라이브러리만 사용)

# 탐지기 평가 (LLM 불필요, 바로 실행됨)
python eval.py

# E2E 데모 — LLM 진단까지 (Ollama + qwen2.5:3b 필요)
python run_demo.py
# 결과: results/report.md, results/chart.svg
```

## 평가 결과

seed를 바꾼 5개 시나리오에서 주입 결함 15건을 전부 탐지했고 오탐은 없었다.

```
결함 재현율: 100% (15/15), 총 오탐: 0건
```

단, 이건 **탐지기를 이 시뮬레이터의 결함 모델에 맞춰 튜닝한 통제 실험**이다.
실제 설비 데이터는 결함 모드가 훨씬 다양하고 라벨도 없어서 이 수치가
그대로 나오지 않는다. 이 데모의 목적은 "탐지 → 근거 전달 → LLM 진단"
파이프라인의 구조를 보여주는 것이다.

실제 LLM 진단 출력 예시 (qwen2.5:3b):

> 진동이 지속적으로 증가하고 있으며, 이와 함께 온도도 상승 추세를 보이고
> 있습니다. 이러한 현상은 베어링 마모 또는 윤활 불량을 의심할 수 있습니다.
> 따라서 정기적인 점검 및 윤활 재공급이 필요하며...

탐지 근거(진동 상승 + 온도 동반 상승)에서 올바른 원인 후보를 짚었다.

## 실데이터 검증: NASA C-MAPSS FD001

"시뮬레이터에서 100%"는 자작 문제를 자작 채점한 것이라, 같은 탐지기를
진짜 벤치마크에 돌려봤다. NASA C-MAPSS FD001 — 터보팬 엔진 100대를
고장까지 운전한 run-to-failure 시계열이다.

```bash
# 데이터: NASA PCoE 저장소에서 받아 data/raw/cmapss/에 압축 해제 (~12MB)
# https://phm-datasets.s3.amazonaws.com/NASA/6.+Turbofan+Engine+Degradation+Simulation+Data+Set.zip
python eval_cmapss.py --k 3.0
```

프로토콜: 열화 추세가 알려진 센서 10개에 EWMA 관리한계 탐지기를 그대로 적용,
서로 다른 센서 2개가 이탈해야 엔진 경보로 인정. RUL은 엔진 1~50의 고장 시점
센서값으로 한계치를 보정하고 엔진 51~100에서만 평가해 라벨 누수를 막았다.

**경보 성능 — 관리한계 kσ 트레이드오프:**

| k | 고장 전 경보 | 리드타임 중앙값 | 수명 초반 30% 조기 경보 |
|---:|---:|---:|---:|
| 4.0σ (합성 튜닝값) | 63/100 | 22 사이클 | 0 |
| 3.5σ | 82/100 | 24 사이클 | 0 |
| 3.0σ | 94/100 | 30 사이클 | 0 |
| 2.5σ | 99/100 | 37 사이클 | 0 |
| 2.0σ | 100/100 | 48 사이클 | 0 |

배운 것 세 가지.

1. **합성 데이터에서 튜닝한 4σ는 실데이터에서 너무 보수적이었다** (63/100).
   3σ로 완화하면 94/100인데 조기 경보는 여전히 0 — 지속성 필터(10사이클)와
   2센서 투표가 노이즈를 이미 걸러주고 있어서 k를 낮출 여유가 있었다.
2. **k=2.0까지 내려도 조기 경보가 0인 건 이 데이터셋의 특성이다.** FD001은
   모든 엔진이 단조 열화하고 끝까지 건강한 엔진이 없어서, 전통적인 오탐율을
   잴 수가 없다. 그래서 "수명 초반 30% 내 경보"를 조기 경보의 대리 지표로
   썼다. 건강한 채 끝나는 운전 데이터가 있다면 이 표의 낮은 k 쪽은
   다르게 나올 것이다.
3. **선형 외삽 RUL은 horizon이 길어지면 무너진다.** 고장 30사이클 전 시점의
   RUL 추정은 MAE 28.5 사이클(중앙값 오차 24), 50사이클 전은 MAE 58.8.
   C-MAPSS의 열화는 뒤로 갈수록 가속하는 곡선이라 최근 30사이클의 선형
   기울기는 남은 수명을 과대평가한다. 지수 열화 모델 피팅이 다음 단계.

## 한계

- 샘플이 1분 간격 RMS라 주파수 영역 분석(FFT, 베어링 결함 주파수)은
  구조상 넣지 않았다. 원파형 데이터를 쓰면 스펙트럼 탐지기를 추가할 수 있다.
- RUL은 선형 외삽 수준의 간이 추정이다 (C-MAPSS 검증에서 한계가 수치로 드러남).
- C-MAPSS는 FD001(단일 운전 조건)만 검증했다. FD002/FD004는 운전 조건이
  6개라 조건별 정규화가 선행되어야 한다.

## 구조

```
pdm/
├── simulator.py   회전기계 센서 시뮬레이터 (결함 주입 + ground truth)
├── detectors.py   z-score / EWMA / 추세 탐지기
├── cmapss.py      NASA C-MAPSS 로더 (열화 방향 통일)
├── diagnose.py    LLM 진단 (Ollama, 근거 제한 프롬프트)
└── report.py      SVG 차트 + markdown 리포트
run_demo.py        E2E 실행
eval.py            시뮬레이터 ground truth 대비 탐지 성능 측정
eval_cmapss.py     NASA C-MAPSS FD001 실데이터 검증
```
