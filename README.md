# pdm-agent

![CI](https://github.com/ckc5800/pdm-agent/actions/workflows/ci.yml/badge.svg)

설비 센서 시계열에서 이상을 탐지하고, LLM이 정비 진단 리포트를 생성하는 예지보전(Predictive Maintenance) 데모.

음성 AI 분야에서 실시간 신호를 다루어 온 경험을 산업 설비 도메인에 적용하기 위해 제작함.
진동 RMS와 음성 파형 모두 시계열에서 이상 패턴을 탐지하는 문제라는 점에서 골격이 동일함.

## 요약

이 문서는 시간순 기록이라 뒤에서 뒤집히는 중간 결론이 앞에 남아 있음. 결론만 먼저 정리.

**검증된 결과** (권장 구성, 근거는 각 절)

| | 구성 | 수치 | 대조군 |
|---|---|---|---|
| 경보 | 전처리 없음, `--k 2.0` | 유효율 93.6~98.0%, **오탐 0~0.9%** | 자명한 예측기 0~1% |
| RUL (공식 test 셋) | `--smooth 5` (+FD003/4는 센서 선택) | MAE 15.8~23.0, 응답률 75~86% | 상수·생존시간 **전 구성에서 이김** |
| LLM 진단 접지 | qwen2.5 3B / 7B | 미접지 0.0% / 1.8% | — |

RUL은 학습 기반 모델(FD001 test RMSE 15~18.5, 전수 응답)에는 응답률·정확도 양쪽에서 뒤짐.
이 접근의 값어치는 정확도가 아니라 라벨과 학습 없이 즉시 배치 가능하다는 데 있음.

결론이 다섯 번 뒤집혔고, 매번 원인은 같음. 자명한 예측기와 비교하지 않은 것.
이 프로젝트의 실질은 예지보전 데모가 아니라 이 기록임.

| # | 처음 결론 | 실제 | 어디서 |
|---|---|---|---|
| 1 | test 셋 MAE가 좋다 | 8개 설정 중 2개는 **상수 예측기에 짐** | [공식 test 셋](#공식-test-셋-평가---split-test) |
| 2 | `savgol`이 MAE 최고 | 응답률이 반토막나 얻은 착시, 마진은 최악 | [필터 계열 비교](#필터-계열-비교---smooth-method) |
| 3 | 평활이 리드타임을 3배로 | 늘어난 만큼 "수명 낭비" 구간으로 감 | [경보 지표 재설계](#경보-지표를-다시-설계하다) |
| 4 | 3B가 접지율 0%로 완벽 | 숫자를 아예 안 써서 통과한 것 | [LLM 접지 검증](#llm-진단-접지-검증-eval_llmpy) |
| 5 | 전처리(융합·평활·센서선택)가 경보를 개선 | 전부 **k 하나로 얻어지는 것**이었다 | [ROC 분석](#roc로-보니-전처리가-하던-일은-k-조정이었다) |

5번이 가장 뼈아픔. k 스윕 표는 첫 라운드부터 이 문서에 있었으나, 포화하는 지표(탐지율)로 읽어 지나침.
방법을 늘리기 전에 지표를 세웠어야 함.

여전히 유효한 것: 조건별 z-정규화(FD002/FD004는 이것 없이 k를 0.5까지 낮춰도 유효율 14%), 지수 RUL 모델, RUL에 대한 평활.

## 설계 원칙: 탐지는 결정적 알고리즘이 담당한다

```
시뮬레이터 ──▶ 이상 탐지 (결정적 알고리즘) ──▶ LLM 진단 (해석·권고만)
 결함 주입      z-score / EWMA / 추세+RUL        탐지 근거 밖 수치 생성 금지
```

이상 탐지는 재현 가능해야 하며 동일 입력에 대해 항상 동일한 결과를 보장해야 함.
따라서 탐지는 통계/신호처리 알고리즘이 수행하고, LLM은 탐지 근거를 종합하여 사람이 읽을 진단(원인 추정·심각도·권고 조치)을 작성하는 역할만 담당.
프롬프트에서 "근거에 있는 수치만 사용"하도록 제한하여 hallucination을 차단함.

## 탐지기 구성

| 탐지기 | 대상 | 방법 |
|---|---|---|
| z-score | 순간 충격 (낙하물, 이물질) | rolling window 기준 z > 5 스파이크 |
| EWMA | 지속적 수준 이탈 (과열 등) | 초기 구간 기준선 + kσ 관리한계 초과 (시뮬레이터 기본 4σ, C-MAPSS 권장 2σ) |
| 추세 | 점진적 열화 (베어링 마모) | 선형회귀 기울기 + 한계치 도달 시간(간이 RUL) 추정 |

시뮬레이터는 회전기계를 단순화한 모델로, 8시간 주기 부하 변동 위에 결함 3종(순간 충격, 점진적 베어링 마모, 일시 과열)을 주입.
주입 시점이 ground truth로 기록되어 탐지기의 정량 평가에 사용됨.

```bash

# E2E 데모 — LLM 진단까지 (Ollama + qwen2.5:3b 필요)
python run_demo.py
# 결과: results/report.md, results/chart.svg

# NASA C-MAPSS 검증 — FD001~FD004 통합 CLI (데이터 준비는 아래 절 참조)

python eval_cmapss.py --fd FD001 --k 2.0                                   # 경보
python eval_cmapss.py --fd FD004 --split test --select-sensors --smooth 5  # RUL

# LLM 진단 접지 검증 (Ollama 필요)
python eval_llm.py --repeat 2
PDM_LLM_MODEL=qwen2.5:7b python eval_llm.py --repeat 2   # 모델 비교

# 단위 테스트 (합성 C-MAPSS 데이터로 평가 파이프라인까지 검증, 실데이터 불필요)
pip install -r requirements-dev.txt
python -m pytest -q
```

## 평가 결과 (시뮬레이터)

seed를 달리한 5개 시나리오에서 주입 결함 15건을 전부 탐지, 오탐 없음.

```
결함 재현율: 100% (15/15), 총 오탐: 0건
```

단, 이는 탐지기를 본 시뮬레이터의 결함 모델에 맞추어 튜닝한 통제 실험임.
실제 설비 데이터는 결함 모드가 훨씬 다양하고 라벨이 없어 동일한 수치를 기대할 수 없음.
본 데모의 목적은 "탐지 → 근거 전달 → LLM 진단" 파이프라인의 구조를 보이는 데 있음.

LLM 진단 출력 예시 (qwen2.5:3b):

> 진동이 지속적으로 증가하고 있으며, 이와 함께 온도도 상승 추세를 보이고
> 있습니다. 이러한 현상은 베어링 마모 또는 윤활 불량을 의심할 수 있습니다.
> 따라서 정기적인 점검 및 윤활 재공급이 필요하며...

탐지 근거(진동 상승 + 온도 동반 상승)로부터 타당한 원인 후보를 제시함.

## 실데이터 검증: NASA C-MAPSS

시뮬레이터 결과는 자체 제작한 문제를 자체 채점한 것이므로, 동일한 탐지기를 공개 벤치마크인 NASA C-MAPSS에 적용하여 검증함.
FD001은 터보팬 엔진 100대를 고장까지 운전한 run-to-failure 시계열.

```bash
# 데이터: NASA PCoE 저장소에서 받아 data/raw/cmapss/에 압축 해제 (~12MB)
# https://phm-datasets.s3.amazonaws.com/NASA/6.+Turbofan+Engine+Degradation+Simulation+Data+Set.zip
python eval_cmapss.py --fd FD001 --k 3.0 --model linear
```

프로토콜: 열화 추세가 알려진 센서 10개에 EWMA 관리한계 탐지기를 그대로 적용하고, 서로 다른 센서 2개가 이탈한 경우에만 엔진 경보로 인정함.
RUL은 엔진 1~50의 고장 시점 센서값으로 한계치를 보정하고 엔진 51~100에서만 평가하여 라벨 누수를 차단함.

**경보 성능 (관리한계 kσ 트레이드오프):**

| k | 고장 전 경보 | 리드타임 중앙값 | 수명 초반 30% 조기 경보 |
|---:|---:|---:|---:|
| 4.0σ (합성 튜닝값) | 63/100 | 22 사이클 | 0 |
| 3.5σ | 82/100 | 24 사이클 | 0 |
| 3.0σ | 94/100 | 30 사이클 | 0 |
| 2.5σ | 99/100 | 37 사이클 | 0 |
| 2.0σ | 100/100 | 48 사이클 | 0 |

주요 관찰은 다음 세 가지.

1. **합성 데이터에서 튜닝한 4σ는 실데이터에서 지나치게 보수적**(63/100).
   3σ로 완화하면 94/100이 되며 조기 경보는 여전히 0건.
   지속성 필터(10사이클)와 2센서 투표가 노이즈를 이미 제거하고 있어 k를 낮출 여지가 있었음.
2. **k=2.0에서도 조기 경보가 0건인 것은 데이터셋 특성에 기인.**
   FD001은 모든 엔진이 단조 열화하며 건강한 상태로 종료되는 엔진이 없음.
   그래서 이 시점에는 오탐율을 잴 수 없다고 보고 "수명 초반 30% 내 경보"를 대리 지표로 사용.
   *(뒤에서 각 엔진의 열화 전 구간을 잘라 음성 클래스를 만들어 실제 오탐율을 잼:
   [오탐율 측정](#없는-음성-클래스를-만들어-오탐율을-잰다).
   그 지표로 보면 이 표에서 가장 좋은 k는 3.0이 아니라 2.0.)*
3. **선형 외삽 RUL은 horizon이 길어질수록 성능이 저하됨.**
   고장 30사이클 전 시점의 RUL 추정은 MAE 28.5 사이클(중앙값 오차 24), 50사이클 전은 MAE 58.8.
   C-MAPSS의 열화는 후반부로 갈수록 가속하는 곡선이어서, 최근 30사이클의 선형 기울기는 잔여 수명을 과대평가함.

### 지수 열화 모델 (`--model exp`)

기준선 대비 편차 d(t)가 지수적으로 증가한다고 가정하고 ln(d)에 선형회귀를 적용하면, 한계 편차 도달 시점이 닫힌식으로 도출됨.

| RUL 모델 | @30사이클 전 | @50사이클 전 |
|---|---|---|
| 선형 외삽 | MAE 28.5 (50/50대 추정) | MAE 58.8 (50/50대) |
| 지수 모델 | **MAE 12.9** (48/50대) | **MAE 23.4** (35/50대) |

오차가 절반 이하로 감소. 다만 지수 모델은 편차가 기준선 위로 충분히 상승하지 않은 엔진에 대해 추정을 보류함(50사이클 전 기준 35/50대만 응답).
응답 정확도와 응답률 간의 트레이드오프이며, 오추정보다 보류가 안전한 정비 계획 관점에서는 실용적인 특성으로 판단됨.

> **이 MAE를 절대 성능으로 읽으면 안 됨.** 본 프로토콜은 "고장 정확히 30(또는 50) 사이클 전" 시점에서 질문하므로 정답이 모든 엔진에서 상수(검증: 정답 집합 {30}, 표준편차 0.0).
> 따라서 **항상 30만 출력하는 예측기가 MAE 0.0을 받음.** 이 지표가 잴 수 있는 것은 고정 horizon에서의 캘리브레이션뿐이며, 다양한 RUL을 구분하는 능력은 재지 못함.
> 위 표는 선형과 지수를 **동일 조건에서 상대 비교**한 값으로만 유효함. 실제 변별력은 라벨이 6~195로 분포하는 아래 공식 test 셋에서 평가해야 함.

### FD002 — 운전 조건 6개 (`--fd FD002`)

FD002는 고도/마하수가 상이한 운전 조건 6개를 오가며 운전된 260대 데이터.
조건 전환 시 센서 절대값이 열화와 무관하게 크게 변동하므로, 동일 탐지기를 그대로 적용하면 **경보가 한 건도 발생하지 않음 (0/130)**.
조건이 혼합된 기준선의 표준편차가 부풀어 관리한계가 도달 불가능한 수준으로 상승하기 때문.

조건별 z-정규화 적용 시 성능이 회복됨.
정규화 통계는 보정 엔진(전반 130대)에서만 계산하고 지표는 평가 엔진(후반 130대)에서만 측정하여 누수를 차단함.

| | 정규화 없음 | 조건별 z-정규화 |
|---|---:|---:|
| 고장 전 경보 (3σ) | 0/130 | 104/130 (조기 경보 0) |
| RUL@30 (지수 모델) | — | MAE 23.7 (109대 추정) |
| RUL@50 (지수 모델) | — | MAE 29.2 (57대 추정) |

단일 조건인 FD001(94/100) 대비 낮은 수치. 조건 전환 노이즈가 잔존하며, FD002 자체가 더 어려운 데이터셋임.
선형 RUL은 여기서도 지수 모델 대비 열세 (MAE 28.5/51.6 vs 23.7/29.2).

"0/130은 k가 높아서 아닌가": 뒤에서 다른 전처리들이 사실은 k 조정을 우회한 것으로 드러났기에, 이 주장도 같은 착시인지 확인함. 정규화 없이 k를 낮추면:

| k (정규화 없음) | 3.0 | 2.0 | 1.5 | 1.0 | 0.5 |
|---|---:|---:|---:|---:|---:|
| FD002 유효 경보율 | 0% | 0% | 0% | 0% | 13.8% (오탐 5.0%) |
| FD004 유효 경보율 | 0% | 0% | 0% | 0% | 14.4% (오탐 10.3%) |

k를 0.5까지 내려도 유효율 14%에 오탐이 붙음. 정규화하면 k=2.0에서 93.6~97.7% / 오탐 0~0.9%.
**조건별 정규화는 k로 대체되지 않는 진짜 전처리.** 조건 전환은 노이즈가 아니라 신호의 좌표계를 바꾸는 문제라 임계값 조정으로는 풀리지 않음.

### FD003/FD004 — 전 데이터셋 확장 (`--fd FD003|FD004`)

FD003은 결함 모드 2개(HPC 열화 + 팬 열화, 단일 조건), FD004는 조건 6개 + 결함 모드 2개로 가장 어려운 조합.
FD004에는 FD002의 조건별 z-정규화를 그대로 재사용함. 네 데이터셋을 동일 프로토콜(k=3.0, 지수 RUL)로 비교하면 다음과 같음.

(경보 열은 k=3.0 기준. 뒤에서 k=2.0이 더 낫다는 것이 밝혀짐)

| 데이터셋 | 조건·모드 | 고장 전 경보 | 리드타임 중앙값 | RUL@30 | RUL@50 |
|---|---|---:|---:|---|---|
| FD001 | 1·1 | 94/100 | 30 | MAE 12.9 (48/50대) | MAE 23.4 (35/50대) |
| FD003 | 1·2 | 96/100 | 32 | MAE 14.8 (48/50대) | MAE 30.2 (30/50대) |
| FD002 | 6·1 | 104/130 | 22 | MAE 23.7 (109/130대) | MAE 29.2 (57/130대) |
| FD004 | 6·2 | 101/125 | 28 | MAE 22.3 (116/125대) | MAE 33.4 (77/125대) |

분모 유의: 다중 조건 셋(FD002/FD004)은 정규화 통계 보정에 사용한 전반부를 제외한 평가 엔진에서만 측정한 값(FD002 260대 중 130대, FD004 249대 중 125대).
단일 조건 셋의 경보는 엔진별 자체 기준선만 사용하므로 전체 엔진에서 측정함.

이전 버전에서는 "결함 모드 구분 없이 단일 한계치를 사용하는 현재 구조로는 FD004 성능이 더 낮을 것"으로 예상하였으나 결과는 달랐음.
난이도를 지배하는 축은 결함 모드 수가 아니라 운전 조건 수 (FD001→FD003은 유지, FD001→FD002는 하락).
결함 모드가 상이해도 본 센서 10개가 포착하는 것은 공통적인 효율 저하이므로, 모드 구분 없는 단일 한계치로도 경보·RUL이 유지된 것으로 해석됨.

### Health index 센서 융합 (`--fuse`)

센서 10개를 각각 초기 30사이클 기준으로 z-정규화한 후 평균하여 단일 지표로 융합함.
방향은 로더에서 이미 통일되어 있으므로 평균만으로 융합이 성립하며, 개별 센서 노이즈가 1/√10로 감소하여 지수 모델이 편차를 더 이른 시점부터 신뢰할 수 있음.
경보 역시 융합 지표 하나로 측정(투표 불필요).

| (k=3.0, exp) | 경보 | 리드타임 | RUL@30 MAE | RUL@50 MAE |
|---|---:|---:|---|---|
| FD001 | 94 → **100**/100 | 30 → **68** | 12.9 (48대) → **10.9 (50/50대)** | 23.4 (35대) → **14.9 (46/50대)** |
| FD002 | 104 → **130**/130 | 22 → **50** | 23.7 (109대) → **11.5 (126/130대)** | 29.2 (57대) → **21.0 (101/130대)** |
| FD003 | 96 → 56/100 | 32 → 70 | 14.8 (48대) → 18.1 (30/50대) | 30.2 (30대) → 23.8 (28/50대) |
| FD004 | 101 → 73/125 | 28 → 56 | 22.3 (116대) → 19.3 (70/125대) | 33.4 (77대) → 28.9 (54/125대) |

단일 결함 모드(FD001/FD002)에서는 전 지표가 일제히 개선: 경보 100%, 리드타임 2배 이상, RUL 오차·보류율 동시 감소.
반면 결함 모드가 2개인 FD003/FD004에서는 경보가 절반 수준으로 하락함.
평균 융합은 "센서 10개가 동일 방향으로 함께 움직인다"는 가정에 의존하는데, 결함 모드별로 센서 시그니처가 상이하면 반응하지 않는 센서들이 신호를 희석하기 때문.
즉 융합의 이득은 이 가정이 성립하는 범위에서만 유효함. FD003/FD004의 리드타임 수치(70/56)는 경보에 성공한 엔진에 한정된 값이므로 해석에 유의.

> **이후 두 번 밀림.** (1) 시간축 평활을 넣으면 융합은 네 데이터셋 모두에서 열세로, 융합은 노이즈 제거의 조잡한 대용품이었음([부수 발견](#부수-발견-평활이-센서-융합을-대체한다)).
> (2) 그 평활조차 경보에서는 k 조정으로 대체됨([ROC 분석](#roc로-보니-전처리가-하던-일은-k-조정이었다)).
> 이 표의 "경보 100%, 리드타임 2배"도 k=3.0 고정 하에서만 개선으로 보임. `--fuse`는 기록을 위해 남겨 두었을 뿐 권장 구성이 아님.

## 전처리 개선: 평활과 데이터 기반 센서 선택

여기까지의 전처리는 사실상 "부호 통일 + 조건별 z-정규화"뿐이었고 노이즈 처리가 없었음.
지수 모델은 30사이클 창에서 ln(d)를 적합하는데, 이 창에 노이즈로 인한 하강이 한 번만 섞여도 `min(d) <= 0`에 걸려 추정을 보류함.
보류율이 높았던 원인이 열화 부재가 아니라 노이즈일 수 있다는 가설.

### 후행 이동평균 (`--smooth N`)

적합 전에 이동평균으로 노이즈를 줄임. **반드시 후행(causal)이어야 함.**
중심 이동평균을 쓰면 t 시점의 평활값이 t 이후 관측을 포함해 "t까지만 보고 추정한다"는 전제가 깨짐. 단위 테스트로 인과성을 고정함.

경보(train 프로토콜, k=3.0)에서 효과가 가장 뚜렷함.

| 셋 | 기준 | `--smooth 5` | `--select-sensors --smooth 5` |
|---|---|---|---|
| FD001 | 94/100 (리드 30) | **100/100 (72)** | 100/100 (92) |
| FD002 | 104/130 (22) | **130/130 (61)** | 130/130 (74) |
| FD003 | 96/100 (32) | **100/100 (73)** | 100/100 (100) |
| FD004 | 101/125 (28) | **125/125 (66)** | 125/125 (94) |

네 데이터셋 모두 경보 100%에 도달, 리드타임이 2~3배가 되었으며, 조기 경보(수명 초반 30%)는 전 구성에서 0을 유지.
놓치던 엔진은 열화가 없어서가 아니라 노이즈에 묻혀 있었던 것.

> **후속 정정 (두 번).** 이 표는 개선의 증거로 삼기에 부적절함.
> 첫째, 탐지율·리드타임은 "무조건 즉시 경보"에 만점을 주는 지표.
> 둘째, 이 비교는 k를 3.0에 고정한 채 잰 것인데 평활은 기준선 σ를 줄여 관리한계를 낮추는 효과가 있어 사실상 "k를 낮춘 것"과 동일. 오탐율을 도입하고 k와 함께 훑으면 **경보에는 평활이 거의 필요 없음.**
> 뒤의 [경보 지표를 다시 설계하다](#경보-지표를-다시-설계하다) 참조.

### MAE가 아니라 대조군 마진으로 읽어야 한다

test 셋 RUL에서는 해석에 주의가 필요함. 평활을 넣으면 **MAE는 오히려 올라감**(FD001 13.4 → 15.8).
응답률이 41%에서 75%로 뛰면서 그동안 포기하던 어려운(수명이 많이 남은) 엔진들이 채점 대상에 들어오기 때문.
앞서 세운 원칙대로 같은 응답 집합의 상수 대조군과 함께 보면 방향이 분명해짐.

| (exp, 125캡, 비융합) | 응답률 | MAE | 상수 대조군 | 마진 |
|---|---:|---:|---:|---:|
| FD001 기준 | 41/100 | 13.4 | 19.7 | −6.3 |
| FD001 `--smooth 5` | 75/100 | 15.8 | 35.7 | **−19.9** |
| FD002 기준 | 91/259 | 15.2 | 14.3 | **+0.9 (패배)** |
| FD002 `--smooth 5` | 169/259 | 18.6 | 33.1 | **−14.5** |
| FD003 기준 | 43/100 | 19.0 | 21.5 | −2.5 |
| FD003 `--select-sensors --smooth 5` | 86/100 | 17.8 | 33.2 | **−15.4** |
| FD004 기준 | 94/248 | 17.8 | 19.6 | −1.8 |
| FD004 `--select-sensors --smooth 5` | 192/248 | 23.0 | 40.7 | **−17.7** |

앞 라운드에서 상수 예측기에 지던 FD002가 +0.9에서 −14.5로 뒤집혔고, 마진이 2 사이클 이하로 애매하던 FD003·FD004도 −15 안팎으로 벌어짐.
MAE만 봤다면 "평활은 성능을 악화시킨다"고 결론 냈을 실험.

창 크기는 5~7이 가장 좋았음(FD001 마진 −19.9/−20.0, FD004 −13.1/−13.1).
10 이상에서는 지연이 커져 마진이 다시 줄고, 선택과 함께 쓰면 조기 경보가 1~2건 발생하기 시작함.
기본값은 평활 없음(`--smooth 1`)으로 두어 이전 수치가 그대로 재현되게 하고, 권장 구성은 아래에 따로 기재.

### 필터 계열 비교 (`--smooth-method`)

이동평균은 상승 추세에서 현재값을 (w−1)/2·기울기만큼 **과소평가**함.
지연이 없는 필터가 더 나을 것이라는 가설로 후행 필터 5종을 붙여 비교함. 전부 causal이며, 인과성은 필터마다 파라미터 테스트로 고정함.

| 필터 | 백색잡음 분산 감쇠 | 추세 지연 | 성격 |
|---|---|---|---|
| `ma` | σ²/w | (w−1)/2·기울기 | 단순 평균 |
| `ewma` | σ²/w (α=2/(w+1)) | 기하급수 꼬리 | 최근 가중 |
| `median` | ≈1.57σ²/w | (w−1)/2·기울기 | 스파이크에 강건 |
| `savgol` | ≈4σ²/w | ~0 | 국소 직선의 끝점 |
| `savgol2` | ≈9σ²/w | ~0 | 국소 2차의 끝점 |

**test 셋 RUL 대조군 마진** (exp, 125캡, w=5, FD003·FD004는 센서 선택 포함):

| 필터 | FD001 | FD002 | FD003 | FD004 |
|---|---:|---:|---:|---:|
| `ma` | **−19.9** | **−14.5** | **−15.4** | −17.7 |
| `ewma` | −18.3 | −13.1 | −13.7 | **−18.6** |
| `median` | −12.1 | −12.5 | −10.9 | −17.0 |
| `savgol` | −13.5 | −8.1 | −13.0 | −16.6 |
| `savgol2` | −9.2 | −5.5 | −13.0 | −16.4 |

**경보**(train, k=3.0, w=5), 리드타임 중앙값, 괄호는 경보 실패 대수:

| 필터 | FD001 | FD002 | FD003 | FD004 |
|---|---:|---:|---:|---:|
| `ma` | **72** | **61** | **100** | **94** |
| `ewma` | 69 | 60 | 95 | 91 |
| `median` | 64 | 54 | 90 | 86 |
| `savgol` | 41 | 31 (2) | 73 | 67 (1) |
| `savgol2` | 33 (2) | 23 (16) | 63 | 60 (10) |

**가설은 틀림.** 지연이 없는 savgol 계열이 모든 지표에서 가장 나쁘고, 순위가 정확히 분산 감쇠력 순서(ma ≈ ewma < median < savgol < savgol2)와 일치함.
이 파이프라인의 두 관문이 모두 지연이 아니라 노이즈에 민감하기 때문. 경보는 관리한계를 넘는지, RUL은 창 안에서 `min(d) > 0`인지를 보는데, 둘 다 한 번의 노이즈 이탈로 결정이 뒤집히는 반면 전체가 균일하게 밀리는 지연에는 거의 영향받지 않음.

여기서도 MAE만 보면 정반대 결론이 나옴. FD002에서 `savgol2`의 MAE는 11.9로 `ma`의 18.6보다 훨씬 좋지만, 응답률이 169/259에서 97/259로 떨어진 결과이고 대조군 마진은 −14.5에서 −5.5로 악화됨.

`ewma`는 `ma`와 사실상 대등함(FD004에서는 오히려 나음). 백색잡음 기준 분산 감쇠가 σ²/w로 정확히 같아서 예상되는 결과. 기본값은 `ma`로 둠.

### 미채택: 스파이크 제거와 엔진별 정규화 (`--despike`, `--normalize-engine`)

| (ma5 대비 마진 변화) | FD001 | FD002 | FD003 | FD004 |
|---|---:|---:|---:|---:|
| 기준 `ma 5` | −19.9 | −14.5 | −15.4 | −17.7 |
| `--despike` (Hampel) | −11.3 | −11.8 | **−16.7** | −16.8 |
| `--normalize-engine` | −17.8 | −12.5 | −12.2 | −14.5 |

**Hampel 스파이크 제거**는 FD003을 제외하면 모두 악화시킴.
C-MAPSS의 노이즈는 단발 스파이크가 아니라 거의 가우시안이라 제거할 스파이크가 없고, 오히려 급격히 진행하는 실제 열화를 이상치로 오인해 중앙값으로 눌러버림.
`median` 필터가 부진한 것과 같은 이유.

**엔진별 초기 구간 z-정규화**도 전 데이터셋에서 악화시킴.
조건별 정규화가 운전 조건 차이만 없애므로 엔진 개체차는 남아 있고, 한계치가 엔진들의 고장 시점 값 중앙값이라 개체 offset이 섞인다는 문제의식이었음.
그러나 지수 모델은 이미 각 엔진의 기준선 평균 μ_b를 빼서 편차로 다루므로 offset은 처리되고 있었고, 추가로 표준편차로 나누는 것이 오히려 해가 됨.
기준선이 조용한 엔진과 시끄러운 엔진의 열화 진폭이 같은 스케일로 눌려 실제 신호 크기 차이가 사라지기 때문.

두 옵션 모두 플래그로 남겨 두되 기본값은 끔으로 유지.

### 데이터 기반 센서 선택 (`--select-sensors`)

기존 센서 10개는 FD001 문헌에서 가져온 고정 목록.
보정 엔진에서 사이클과의 상관을 재어 |r| ≥ 0.4인 센서와 그 부호를 직접 고르게 함(평가 엔진이 섞이면 센서 선택 자체가 누수이므로 보정 엔진만 사용).

| 셋 | 선택 결과 | 고정 목록 대비 |
|---|---|---|
| FD001 / FD002 / FD003 | 14개 | **+s8, s9, s13, s14** |
| FD004 | 10개 | +s8, s9, s13, s14 / −s7, s12, s20, s21 |

고정 목록은 강한 신호 4개를 통째로 빠뜨리고 있었음. FD004에서는 이 넷이 상위권(|r| 0.72~0.82)인 반면 제외된 s7·s12·s20·s21은 0.30~0.33에 불과.
효과는 데이터셋 성격에 따라 갈림. 결함 모드가 2개인 FD003(−9.6 → −15.4)과 FD004(−13.1 → −17.7)에서는 뚜렷이 개선되지만, FD001(−19.9 → −16.9)과 FD002(−14.5 → −9.2)에서는 오히려 나빠짐.
고정 목록이 FD001 기준으로 만들어졌으니, 그 목록이 안 맞는 데이터셋에서만 이득이 나는 것이 앞뒤가 맞음.

### 부수 발견: 평활이 센서 융합을 대체한다

앞서 도입한 health index 융합은 개별 센서 노이즈를 1/√10로 줄이는 것이 목적이었음. 그런데 시간축 평활을 넣고 나면 융합은 오히려 손해.

| (exp, 125캡) 마진 | 융합, 평활 없음 | 비융합, `--smooth 5` |
|---|---:|---:|
| FD001 | −16.2 | **−19.9** |
| FD002 | −7.0 | **−14.5** |
| FD003 | +0.4 | **−9.6** |
| FD004 | −3.9 | **−13.1** |

네 데이터셋 전부 평활 쪽이 나음. 융합은 노이즈 제거의 조잡한 대용품이었고, 그 대가로 센서 간 다양성과 투표 능력을 잃고 있었음.
융합이 FD003/FD004에서 경보를 반토막 냈던 이유도 같은 맥락으로 설명됨. 결함 모드마다 다른 센서가 반응하는데 평균이 그것을 뭉갠 것.

## 경보 지표를 다시 설계하다

위의 "평활 5 권장"은 틀림. 그것을 드러낸 것은 경보 지표에 자명한 대조군을 붙인 일.

### 탐지율과 리드타임만 보면 상수 예측기가 만점을 받는다

지금까지 경보를 "고장 전에 울렸는가(탐지율)"와 "얼마나 일찍 울렸는가(리드타임)"로만 재 왔음.
그런데 기준선이 끝나자마자 전 엔진에 무조건 경보하는 예측기를 생각해 보면, 탐지율 100%에 리드타임 최대를 받음. 두 지표 모두 만점. 경보가 아니라 상수 출력인데도 그러함.

RUL에서 상수 대조군으로 겪은 것과 같은 결함이었고, 평활을 넣을수록 리드타임이 30 → 72 → 88로 늘어나 "개선"으로 보였던 것이 바로 이 방향.
즉 그동안 최적화하던 지표는 퇴화 예측기를 향해 상을 주고 있었음.

### 운용 관점 4분류

정비 계획에서 쓸모 있는 경보는 "너무 늦지도 너무 이르지도 않은" 것. 예고 시간(경보 시점의 실제 잔여 수명)으로 분류.

| 분류 | 조건 | 의미 |
|---|---|---|
| `actionable` | 예고 20~100 사이클 | 정비 일정을 잡을 수 있는 유효 경보 |
| `late` | 예고 < 20 | 울리긴 했으나 대응할 시간이 없음 |
| `early` | 예고 > 100 | 고장은 맞혔지만 멀쩡한 잔여 수명을 버림 |
| `missed` | 경보 없음 | 놓침 |

자명한 대조군은 이 지표에서 **유효율 0~1%** 로 무너짐(전부 `early`).
FD001 기준선 탐지기는 75%로, 지표가 실제 경보 능력을 재고 있다는 확인.

### 다시 잰 최적 구성

유효율(%), 평활 창 × 센서 선택 격자:

| 셋 | 센서 | w=1 | w=2 | w=3 | w=4 | w=5 | w=7 |
|---|---|---:|---:|---:|---:|---:|---:|
| FD001 | 고정 | 75.0 | **97.0** | 90.0 | 86.0 | 83.0 | 74.0 |
| FD001 | 데이터 | 89.0 | 89.0 | 80.0 | 72.0 | 68.0 | 57.0 |
| FD002 | 고정 | 47.7 | 92.3 | **95.4** | 92.3 | 90.0 | 83.1 |
| FD002 | 데이터 | 68.5 | 90.0 | 88.5 | 83.1 | 75.4 | 67.7 |
| FD003 | 고정 | 81.0 | **96.0** | 92.0 | 85.0 | 78.0 | 66.0 |
| FD003 | 데이터 | 83.0 | 76.0 | 68.0 | 61.0 | 53.0 | 43.0 |
| FD004 | 고정 | 59.2 | 88.0 | **93.6** | 91.2 | 86.4 | 73.6 |
| FD004 | 데이터 | 73.6 | 69.6 | 68.0 | 65.6 | 59.2 | 48.0 |

두 가지가 뒤집힘.

1. **최적 평활은 5가 아니라 2~3.** w=5는 FD003에서 유효율을 96% → 78%로 떨어뜨림.
   리드타임을 늘리는 것이 곧 개선이 아니었고, 늘어난 리드타임의 상당 부분이 `early`(수명 낭비)로 넘어가고 있었음.
2. **데이터 기반 센서 선택은 경보를 악화시킴.** 센서가 10개에서 14개로 늘면 `VOTES=2` 요건이 더 쉽게 차서 경보가 빨라지고, 그만큼 `early`가 됨.
   앞 절에서 이것이 이득으로 보였던 이유도 리드타임으로 쟀기 때문.

### 없는 음성 클래스를 만들어 오탐율을 잰다

위의 `early`는 오탐의 대리 지표일 뿐임. C-MAPSS는 전 엔진이 고장까지 운전되어 "건강한 채 끝나는" 엔진이 없고, 그래서 지금까지 오탐율을 잴 수 없었음.

그러나 각 엔진의 앞부분은 실제로 건강함. 문헌이 RUL 타깃을 piecewise-linear로 두고 knee(관례상 125) 이전을 상수 구간으로 보는 것과 같은 근거.
잔여 수명이 knee를 넘는 구간만 잘라 탐지기에 넣으면, 거기서 울리는 경보는 정의상 오탐.

```
건강 구간의 끝 = 시계열 길이 + (끝 시점의 잔여 수명) − knee
```

run-to-failure인 train은 끝 잔여 수명이 0, 절단된 test는 라벨을 넣으면 되므로 같은 식이 두 프로토콜에 그대로 적용됨.
표본도 충분함. FD001 79대, FD004 218대가 판정 가능한 길이(≥45 사이클)의 건강 구간을 가짐.
구간이 짧아 제외된 엔진 수는 분모를 조용히 바꾸지 않도록 함께 보고.

### ROC로 보니 전처리가 하던 일은 k 조정이었다

유효 경보율 / 오탐율 (FD001):

| 평활 w | k=2.0 | k=2.5 | k=3.0 | k=3.5 | k=4.0 | k=5.0 |
|---:|---|---|---|---|---|---|
| 1 | **95/0.0** | 92/0.0 | 75/0.0 | 57/0.0 | 39/0.0 | 15/0.0 |
| 2 | 86/5.1 | 91/2.5 | **97/0.0** | 91/0.0 | 80/0.0 | 56/0.0 |
| 3 | 79/10.1 | 87/3.8 | 90/2.5 | **98/0.0** | 94/0.0 | 79/0.0 |
| 5 | 56/19.0 | 74/11.4 | 83/6.3 | 88/2.5 | 90/2.5 | **94/0.0** |

각 행의 최적점이 오른쪽으로 밀림. 평활을 키울수록 더 큰 k가 필요함.
이유는 기계적. 평활은 기준선 표준편차를 1/√w로 줄이지만 열화 신호는 줄이지 않으므로, 관리한계 μ + kσ가 신호 기준으로는 그만큼 좁아짐. 실측이 정확히 그러함:

| w | 기준선 σ | σ 비율 | 1/√w 예측 | 오탐 0인 최적 k | k 비율 |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.2887 | 1.00 | 1.00 | 2.0 | 1.00 |
| 2 | 0.2044 | 1.41 | 1.41 | 3.0 | 1.50 |
| 3 | 0.1645 | 1.75 | 1.73 | 3.5 | 1.75 |
| 5 | 0.1259 | 2.29 | 2.24 | 5.0 | 2.50 |

즉 **경보에서 평활과 k는 같은 손잡이.** 그렇다면 k만 조정해도 같은 곳에 도달할 수 있어야 함. 평활 없이 k만 훑으면:

| 셋 | 평활 없이 최적 | 평활 최적 | 차이 |
|---|---|---|---|
| FD001 | 95.0 / 0.0 (k=2.0) | 98.0 / 0.0 (w=3, k=3.5) | 평활 +3.0 |
| FD002 | **98.5 / 0.0** (k=1.75) | 95.0 / 0.0 (w=3, k=3.0) | 평활 −3.5 |
| FD003 | **98.0 / 0.0** (k=2.0) | 97.0 / 0.0 (w=2, k=3.5) | 평활 −1.0 |
| FD004 | **93.6 / 0.9** (k=2.0) | 94.0 / 2.8 (w=3, k=3.0) | 오탐 3배 |

앞 절의 "평활이 경보를 극적으로 개선한다"는 결론은 k를 3.0에 고정한 채 잰 것이었음.
평활이 실질적으로 한 일은 관리한계를 낮춘 것이고, 그건 k를 직접 낮추면 지연 없이 얻을 수 있음. 네 셋 중 셋에서 평활은 이득이 없거나 손해.

이 프로젝트의 첫 라운드에 이미 k 스윕 표가 있었음(4.0σ~2.0σ).
그때 탐지율로만 판단해 "k=3.0이면 94/100"에서 멈췄고, 이후 융합·평활·센서 선택으로 우회해 얻으려 한 것의 상당 부분을 k 하나가 이미 갖고 있었음.
지표를 제대로 세우는 일이 방법을 늘리는 일보다 먼저.

단, 이것은 **경보에 한정된 결론**임. RUL에서는 평활이 응답률(41→75%)과 대조군 마진(−6.3→−19.9) 양쪽을 실제로 개선했고, 그 측정에는 상수 대조군이 이미 붙어 있었음.

### 경보와 RUL은 서로 다른 전처리를 원한다

| 목적 | 최적 구성 | 근거 |
|---|---|---|
| 경보 | **전처리 없음 + `--k 2.0`** | 유효율 93.6~98.0%, 오탐 0~0.9% |
| RUL | `--smooth 5`, FD003·FD004는 `--select-sensors` | 대조군 마진 −15 ~ −20 |

같은 파이프라인이지만 두 출력의 최적점이 정반대. 경보는 임계값 하나로 충분하고, RUL은 노이즈 억제가 실제로 필요.
하나의 구성으로 억지 통일하지 않고 목적별로 나누는 편이 타당함.

```bash
# 경보 중심 — 전처리 없이 임계값만
python eval_cmapss.py --fd FD001 --k 2.0

# RUL 중심 (test 셋)
python eval_cmapss.py --fd FD004 --split test --select-sensors --smooth 5
```

기본값(`--smooth 1`, 고정 센서)은 그대로 두어 이 문서의 모든 수치가 재현되게 함.

## 공식 test 셋 평가 (`--split test`)

앞의 train 프로토콜은 자체 설계이므로 문헌 수치와 직접 비교할 수 없음.
공식 test 셋은 각 엔진이 고장 전 임의 시점에서 절단되어 있고 해당 시점의 실제 RUL 라벨(`RUL_FDxxx.txt`)이 제공되므로, 문헌의 RMSE/PHM08 score와 동일한 조건.
train 전체로 한계치(및 FD002/FD004의 정규화 통계)를 보정하고, test 각 엔진의 마지막 사이클에서 RUL을 추정하여 라벨과 비교함.

전제할 차이점: 본 추정기는 열화가 관측되지 않으면 추정을 보류함.
라벨이 RUL 6~195 사이클까지 분포하는데 수명 중반의 엔진에는 열화 신호 자체가 없어, 응답률이 24~61%에 그침.
따라서 아래 수치는 열화가 관측된 엔진에 한정된 성능이며, 전수 응답하는 학습 기반 모델과의 직접 비교에는 적합하지 않음.

부분집합에 매긴 점수는 그 자체로는 해석이 불가능함.
그래서 동일한 응답 집합에 "항상 그 집합의 라벨 중앙값"을 출력하는 상수 예측기를 함께 돌려 대조군으로 삼음.
상수를 못 이긴다면 그 MAE는 추정 능력이 아니라 집합 선택의 산물.

여기에 더 강한 대조군을 하나 더 추가. **생존시간 예측기**는 센서를 전혀 읽지 않고 `RUL = (train 엔진 수명 중앙값 − 경과 사이클)`만 답함.
엔진이 얼마나 오래 돌았는지만 알아도 이 정도는 맞히므로, 이것을 못 이기면 센서를 읽는 의미가 없음.

| (exp, 125캡) | 추정기 MAE | 상수 | 생존시간 | 판정 |
|---|---:|---:|---:|:--|
| FD001 고정 w5 | 15.8 | 35.7 | 32.7 | 둘 다 이김 |
| FD002 고정 w3 | 14.9 | 26.7 | 32.2 | 둘 다 이김 |
| FD003 데이터 w3 | 16.7 | 30.5 | 39.3 | 둘 다 이김 |
| FD004 데이터 w3 | 21.6 | 39.7 | 52.8 | 둘 다 이김 |

전 구성에서 두 대조군을 모두 이김. 특히 FD004는 21.6 vs 50.7로 격차가 큼.
수명 편차가 큰 데이터셋일수록 경과 시간만으로는 맞히기 어렵고, 센서를 읽는 값어치가 커짐.
상수와 생존시간 중 어느 쪽이 더 강한지는 데이터셋마다 다르므로(FD001은 생존시간, FD002·FD003·FD004는 상수) 둘 다 보고.

| test 셋 (exp, 추정 125캡) | 응답률 | MAE | RMSE | 상수 대조군 MAE | 판정 |
|---|---:|---:|---:|---:|:--|
| FD001 | 41/100 | 13.4 | 20.9 | 19.7 | 이김 (−6.3) |
| FD001 `--fuse` | 61/100 | 14.6 | 19.5 | 30.8 | 이김 (−16.2) |
| FD002 | 91/259 | 15.2 | 24.3 | 14.3 | **못 이김 (+0.9)** |
| FD002 `--fuse` | 128/259 | 18.6 | 25.3 | 25.6 | 이김 (−7.0) |
| FD003 | 43/100 | 19.0 | 28.0 | 21.5 | 이김 (−2.5) |
| FD003 `--fuse` | 29/100 | 21.8 | 25.8 | 21.4 | **못 이김 (+0.4)** |
| FD004 | 94/248 | 17.8 | 27.1 | 19.6 | 이김 (−1.8) |
| FD004 `--fuse` | 59/248 | 15.0 | 19.1 | 18.9 | 이김 (−3.9) |

**8개 설정 중 2개에서 추정기가 상수 예측기에 짐.** 이긴 경우에도 FD003·FD004 비융합은 마진이 2 사이클 안팎으로 통계적 우위라 부르기 어려움.
뚜렷한 우위는 FD001(특히 융합, −16.2)에 한정됨.
참고로 같은 상수를 전체 엔진에 적용하면 MAE가 35.8~46.5로 뛰므로, 위 대조군 수치가 낮다는 것 자체가 응답 집합이 얼마나 쉬운 쪽으로 치우쳤는지를 보여줌.

**문헌 대비 위치.** FD001 test 셋에 보고된 RMSE는 학습 기반 모델 기준 다음과 같음.
이들은 모두 100대 전수에 응답한 결과이며, 학습 시 RUL 타깃을 125 내외로 캡하므로 본 표의 캡 적용 수치와 비교 조건이 같음.

| 방법 | FD001 test RMSE | 확인한 출처 |
|---|---:|---|
| LSTM | 14.931 | [1] Table III |
| Deep LSTM (Zheng et al. 2017) | 16.14 | [1] Table III, [2] Table 4 |
| Ridge Regression (선형) | 16.634 | [1] Table III |
| 1D CNN | 16.971 | [1] Table III |
| CNN (Babu et al. 2016) | 18.45 | [2] Table 4 |

[1] Galchar, Goel, Kanu, *Remaining Useful Life Estimation for Turbofan
Engines: A Comparative Study of Classical, CNN, and LSTM Approaches*,
[arXiv:2604.27234](https://arxiv.org/html/2604.27234v1) ·
[2] *Data-driven Prognostics with Predictive Uncertainty Estimation using
Ensemble of Deep Ordinal Regression Models*,
[arXiv:1903.09795](https://arxiv.org/pdf/1903.09795)

본 추정기의 최고 성능은 융합 적용 시 RMSE 19.5이며, 그것도 100대 중 61대에만, 그것도 쉬운 쪽으로 치우친 61대에만 응답한 결과.
즉 응답률과 정확도 양쪽에서 학습 기반 모델에 뒤짐.
특히 선형 Ridge Regression이 전수 응답으로 16.6을 기록한다는 점은, 격차의 원인이 "딥러닝이 아니라서"가 아니라 학습 없이 외삽만으로는 한계가 있다는 데 있음을 보여줌.

본 접근의 의의는 정확도 경쟁이 아니라 **라벨과 학습 없이 즉시 배치 가능하다는 점**에 있음.
신규 설비처럼 고장 이력이 없어 지도학습이 불가능한 초기 단계에서, 조건별 정규화와 관리한계만으로 경보를 내고 열화가 뚜렷한 구간에 한해 RUL을 제시하는 용도.

융합의 효과는 test 셋에서도 갈림: FD001은 응답률이 41→61%로 오르면서 오차가 유지되었고, FD004는 응답률이 하락하는 대신 응답 엔진의 오차·score가 개선되었으며, FD002는 응답률은 오르나 MAE가 악화됨.

### 미채택 실험: 최소 근거 센서 요건 (`--min-sensors`)

RUL 추정은 "상승 추세이고 한계치까지 여유가 있는" 센서만 골라 중앙값을 취함.
경보는 서로 다른 센서 2개를 요구하는데(`VOTES=2`) RUL에는 그런 요건이 없어, FD001 응답 엔진의 7대는 센서 단 1개에 근거하고 있었음.
그래서 경보와 같은 방식으로 최소 근거 센서 수를 올려 봄.

| FD001 (exp, 125캡) | 응답 | MAE | 상수 대조군 | 마진 |
|---|---:|---:|---:|---:|
| `--min-sensors 1` (현행) | 41/100 | 13.4 | 19.7 | −6.3 |
| `--min-sensors 2` | 34/100 | 9.5 | 14.7 | −5.2 |
| `--min-sensors 3` | 30/100 | 7.9 | 10.9 | −3.0 |

MAE만 보면 13.4 → 7.9로 크게 좋아짐. 그러나 상수 대조군도 19.7 → 10.9로 함께 내려가고, 마진은 오히려 −6.3 → −3.0으로 줄어듦.
즉 개선의 정체는 추정 능력 향상이 아니라 쉬운 엔진만 남기는 선택 효과.
FD004에서는 min 2 이상에서 아예 상수에 지고(12.3 vs 12.1), FD002는 어느 값에서도 이기지 못함. 따라서 기본값은 1로 두고 미채택.
대조군 없이 MAE만 봤다면 정반대 결론을 내렸을 실험이라 기록으로 남김.

### PHM08 score 해석 주의

PHM08 score는 늦은 예측에 지수 벌점을 부과하므로 과대추정 소수 건에 전체가 지배됨.
FD001 캡 미적용 원점수 1.56×10⁹은 그 100.0%가 단 한 대(오차 +211.7 → e²¹·¹⁷)에서 나옴. 다음으로 큰 항은 325.4, 206.9에 불과.
추정치를 125 사이클로 캡하면(문헌의 piecewise-linear RUL 타깃과 동일한 발상) 779.4로 내려감.

또한 score는 **합계라서 엔진 수에 비례**함.
41대에 대한 합을 100대에 대한 문헌 합과 나란히 놓으면 안 되므로, JSON과 출력 모두 원점수·캡 점수와 함께 `phm08_per_engine`을 기록.

## LLM 진단 접지 검증 (`eval_llm.py`)

이 프로젝트의 첫 문단은 "LLM에게 탐지를 시키지 않는다"이고, 그 장치가 "탐지 근거에 있는 수치만 사용하라"는 프롬프트 제약.
그런데 그 제약이 지켜지는지는 한 번도 측정한 적이 없었음. 헤드라인 주장이 검증되지 않은 채 남아 있었음.

```bash
python eval_llm.py --repeat 2              # Ollama 필요
PDM_LLM_MODEL=qwen2.5:7b python eval_llm.py --repeat 2
```

진단문에서 숫자를 추출해 LLM에 넘긴 근거 텍스트의 수치와 대조하고, 근거에 없는 값을 미접지로 셈.
근거는 프롬프트를 조립하는 함수(`diagnose.build_evidence`)가 그대로 돌려주므로 모델이 실제로 본 것과 검사 대상이 어긋나지 않음.

### 검사기를 먼저 고정했다 — 그리고 두 번 틀렸다

채점기 결함은 모델의 hallucination으로 오인됨. 합성 케이스로 규칙을 먼저 고정했는데도, 실측을 돌려 보니 두 가지가 더 나옴.

1. **설비 ID의 숫자를 측정값으로 셈.** 첫 실측에서 미접지율이 100%로 나왔는데, 원인은 모델이 `PUMP-01`을 그대로 옮겨 쓴 것을 "지어낸 수치 01"로 집계한 것.
   식별자(영문자 뒤에 붙은 숫자, 센서명 `s21` 포함)를 제외하도록 수정.
2. **상대 허용오차가 너무 헐거움.** 반올림 표기를 감안해 5%를 허용했는데, 시간 인덱스처럼 값이 크면 5%가 100을 넘음.
   근거의 `2580`을 `2680`으로 바꿔 쓴 것이 통과하고 있었음. 표기 자릿수가 함의하는 반올림 폭(소수 1자리 → ±0.05, 정수 → ±0.5)으로 변경.

둘 다 회귀 테스트로 고정. 측정 도구를 먼저 고정하지 않으면 이런 결함이 그대로 모델 평가 결과가 됨.

### 결과 — 모델 크기가 바꾸는 것

seed 5개 × 2회 = 10회 실행:

| | qwen2.5:3b | qwen2.5:7b |
|---|---:|---:|
| 진단문의 수치 총량 | 12개 | **109개** |
| 미접지 | 0개 (0.0%) | 2개 (1.8%) |
| 미접지 0건인 실행 | 10/10 | 8/10 |
| **숫자를 하나도 안 쓴 실행** | **6/10** | 0/10 |
| 탐지 센서 언급률 | 100% | 100% |

접지율만 보면 3B가 완벽(0%)하고 7B가 열등(1.8%)해 보임.
그러나 3B는 10회 중 6회를 숫자 없이 서술해서 이긴 것으로, 수치를 쓰지 않으면 접지 검사를 자동으로 통과함.
세 번째로 만난 같은 함정이라 "탐지된 센서를 실제로 언급했는가"를 함께 재도록 지표를 보강(둘 다 100%).

7B의 미접지는 구체적. 근거는 `vibration (1008~1032분)`인데 진단문은 `진동(1008~1350분, 1866~3959분)`이라고 씀. 구간의 시작값은 정확히 인용하고 끝값을 지어낸 것.
프롬프트 제약이 완전히 무력하지는 않지만(107/109 접지), 결정적 탐지와 LLM 서술을 분리한 설계가 필요한 이유를 보여주는 실제 사례. 탐지 결과 자체는 이 오류에 영향받지 않음.

정리하면 **구체성과 충실성 사이의 트레이드오프**. 3B는 안전하지만 정보량이 적고, 7B는 8배 더 구체적인 대신 1.8%를 지어냄.
리포트 용도로는 7B가 낫고, 수치가 그대로 정비 지시로 이어지는 환경이라면 3B의 보수성이나 후처리 검증(이 `eval_llm.py`를 파이프라인에 넣는 것)이 필요.

## 한계

**측정 가정에 붙은 한계**

- 오탐율은 "잔여 수명 > 125면 건강하다"는 문헌 관례(piecewise-linear RUL의 knee)를 빌린 정의 위에 있음.
  실제 열화 시작 시점은 엔진마다 다르므로 절대적 오탐율이 아니라 동일 가정 아래 구성 간 비교에 쓰는 수치.
  knee를 낮추면 건강 구간이 길어져 오탐율이 올라감.
- 경보 유효 구간(예고 20~100 사이클)은 정비 리드타임을 가정한 값이며 설비·조직마다 다름. 이 경계를 바꾸면 최적 k도 함께 움직임.
- 네 데이터셋 모두 건강한 채 종료되는 엔진이 없음.
  위 오탐율은 각 엔진의 앞구간을 잘라 만든 것이라, 정상 설비만 장기간 운전한 데이터로는 재검증되지 않음.
- train 프로토콜의 RUL 지표는 정답이 고정 상수(30/50)라 변별력이 없음.
  선형 대 지수의 상대 비교에만 썼고, 절대 성능은 공식 test 셋으로만 서술함.

**성능의 한계**

- RUL은 외삽 기반 간이 추정이라 열화가 안 보이면 답을 보류함(권장 구성에서 응답률 75~86%, 전처리 없이는 24~61%).
  정비 계획에는 보류가 안전하지만, 전수 응답하는 학습 모델(FD001 test RMSE 15~18.5)과는 응답률·정확도 양쪽에서 비교가 안 됨.
- RUL의 대조군 우위는 구성에 민감함.
  권장 구성(`--smooth 5`)에서는 상수·생존시간 대조군을 전 구성에서 이기지만, 전처리 없는 기본 구성에서는 8개 중 2개를 짐. **평활 없이 쓰지 말 것.**
- 샘플이 1분 간격 RMS라 주파수 영역 분석(FFT, 베어링 결함 주파수)은 구조상 제외함. 원파형 데이터가 있으면 스펙트럼 탐지기를 추가할 수 있음.

**탐색하지 않은 것**

- 경보는 k × 평활창 격자를 훑었지만, RUL은 `ma`/`w=5` 기준으로만 맞춤.
  필터별 최적 w는 다를 수 있음(지연이 없는 savgol은 더 큰 w를 감당할 여지).
- 평활은 지연을 유발하므로 급격한 고장 모드(스텝형 이상)에는 불리함.
  본 데이터셋들은 모두 점진적 열화라 이 위험이 드러나지 않았고, 시뮬레이터의 순간 충격 탐지에는 평활을 적용하지 않음.
- Health index 융합은 "센서들이 동일 방향으로 움직인다"는 단일 결함 모드 가정에 의존함.
  평활 도입 후 모든 셋에서 열세여서 사실상 대체된 기능으로 보며, 모드별 지표 분리는 미구현.
- LLM 접지 검증은 시나리오 5개 × 2회뿐임.
  실행마다 출력이 달라지므로(3B는 12~14개 수치, 7B는 109~110개) 표본을 늘려야 1.8%라는 미접지율의 신뢰구간을 말할 수 있음.
